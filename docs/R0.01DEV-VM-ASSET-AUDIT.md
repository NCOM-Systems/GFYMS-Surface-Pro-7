# R0.01DEV VM and asset audit

**Source report:** [`RANTS/R0.01DEV/R0.01DEV.md`](https://github.com/NCOM-Systems/GFYMS-Surface-Pro-7/blob/main/RANTS/R0.01DEV/R0.01DEV.md)

**Audited against:** GitHub `main` at `f6f3eda` (2026-10-01)

## What the report is

`R0.01DEV.md` is a product-feedback and architecture requirements document with embedded screenshots. It is not yet a reproducible VM test record: it does not identify the ISO checksum, Git commit, hypervisor/version, guest RAM/CPU/storage, firmware mode, display configuration, network mode, boot logs, or pass/fail assertions. It should be retained as the product brief, but future VM testing should produce a separate evidence packet with those fields.

The report is still valuable because it establishes a coherent development/testing direction rather than asking for blind rewrites:

- first-boot setup and hardware/storage/driver discovery;
- a usable GFYMS Center with Updates, rollback, Feedback, Discussions and Apple Find My flows;
- VM detection with a clear distinction between physical, virtual, passed-through and unavailable hardware;
- OuijaBoard as a separate diagnostics and hardware-test environment;
- virtual/phantom Surface devices and controllable sensor states;
- a live, privacy-conscious diagnostic diary;
- a staged priority model that keeps Android and a kernel below the initial development infrastructure.

## Current implementation reality

The repository has documentation and some supporting pieces, but the report's P0/P1 systems are not all implemented:

- `docs/GFYMS-CENTER.md` documents Updates, package rollback, Feedback/Discussions behavior, and the Surface Pen control categories. This is a contract, not proof that every UI flow is implemented and hardware-qualified.
- The repository contains GFYMS Center packaging and Apple Find My package sources, but the VM report's OuijaBoard service, live event console, phantom device framework, sensor simulator, VM startup policy, and virtual networking lab are not present as a complete tracked subsystem.
- The existing recovery and diagnostic tooling is evidence-oriented, which is the correct foundation for a VM test diary. It should be extended rather than replaced with a giant always-on developer console.
- The Android APK and Android kernel items are correctly classified as P3. They must remain disabled in the base ISO until a bootable, signed x86_64 Android userspace and hardware adapters exist.

## Recommended implementation order

### P0-A — test contract and VM detection

Create a small read-only `gfyms-vm-report` command that records DMI virtualization facts, hypervisor, kernel/boot mode, CPU/RAM, display, storage, network, USB, detected Surface capabilities, package versions and boot failures. Give the report a schema version and a redaction mode. Do not enable remote reporting by default.

VM detection should only select a development profile. It must not claim that virtual devices are real Surface hardware, and it must not automatically run privileged emulation code in a normal physical install.

### P0-B — OuijaBoard boundary

Implement OuijaBoard as a separate service/API boundary with:

1. a read-only event stream for logs and state changes;
2. an explicit virtual-device registry;
3. capability labels such as `physical`, `virtual`, `passthrough`, `missing` and `unsupported`;
4. a permissioned command channel for simulation;
5. a local-only default transport, such as a Unix socket with strict ownership and access control;
6. journal integration and bounded event retention.

Start with a virtual keyboard attachment, tablet-mode state and accelerometer fixture. Do not start with camera or IPU4 emulation; camera behavior needs a separate pipeline contract and would otherwise create misleading confidence.

### P1 — Center usability

Fix the report's concrete UX issues before adding advanced emulation:

- Discussions must open an actual discussion URL or clearly state that it is unavailable; it must never render a README as if it were a discussion system.
- Apple Find My needs explicit states: configured, partial, authentication required, unavailable, corrupted and unsupported VM.
- Updates must show source, signature/hash status, target package, rollback availability and reboot requirements.
- First boot should be a resumable wizard, not a privileged monolith. Hardware detection can be read-only first; changes should be explicit and reversible.

### P1 — test fixtures

Add deterministic fixtures for device attach/detach, sensor ranges, thermal warnings, failed units, network changes and package rollback. Every fixture should run without real hardware and should be clearly marked virtual in the UI and event stream.

### P2 — advanced simulation

Only after the core event and capability model is stable should OuijaBoard add virtual Wi-Fi/VPN/Bluetooth and dynamic MAC testing. These features need namespace isolation and must never alter the host's real network identity.

## VM report corrections to make in future

The screenshots demonstrate UI intent, but they do not establish that an ISO boots or that hardware services work. A future report should include:

- ISO filename, SHA-256 and Git commit;
- VM software and version;
- UEFI/BIOS mode, Secure Boot state and virtual hardware profile;
- guest memory, vCPUs, disk bus, graphics adapter, display resolution and network mode;
- a boot timeline with timestamps;
- command output for `systemctl --failed`, `journalctl -b -p warning`, package verification and kernel/modules;
- a test matrix with `PASS`, `FAIL`, `BLOCKED` or `NOT RUN`;
- the exact failure log and expected behavior for every failed item.

The report also links to an expiring LimeWire ISO. That is unsuitable as a reproducible release source. The GitHub Actions artifact is the authoritative build output; long-term distribution needs a stable release host with checksums and retention guarantees.

## Asset audit

The live `assets/` directory contains eight raster assets:

- four Surface device hero images;
- black and white NCOM Systems full hero logos;
- black and white OuijaBoard logos.

The assets are useful, but they are not yet a canonical brand system:

- There is no `gfyms-logo.svg` or canonical `gfyms-logo.png`, despite the assets README requesting both.
- The files use inconsistent raster dimensions and naming conventions.
- The device hero images visibly include large colored or dark background fields instead of consistently cropped transparent cutouts. That will create poor results on both light and dark README themes.
- `OijaBoard` is misspelled in the filenames; the product requirements consistently call it `OuijaBoard`. Existing filenames should not be deleted casually, but new canonical names and compatibility aliases should use the correct spelling.
- The white and black NCOM logos are reasonable light/dark variants, but they are raster-only and need an SVG source before being used as the single source for README, ISO, KDE and social-preview branding.
- The asset README says the user's logo is absent even though NCOM and OuijaBoard raster marks are now present. It should describe the current assets honestly and state which file is provisional.

Recommended asset work is non-destructive: preserve the existing files, add a canonical SVG and transparent PNG exports, add a small asset manifest with dimensions/background/usage, and use the same approved mark across README, ISO fastfetch, installer and desktop branding. Do not regenerate or replace the user's personal mark without approval.

## Bottom line

The report should drive a **VM qualification and development-tools milestone**, not be treated as proof that the ISO already has native Surface emulation. The highest-value next implementation is a small, auditable VM report plus an isolated OuijaBoard event/capability API. That makes the later pen, sensors, recovery, camera and driver work testable without confusing virtual success with physical Surface qualification.
